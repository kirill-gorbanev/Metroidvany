# Пересоздание системы по устаревшему коду

Цель: получить новую систему, которая умеет всё, что умела старая и что хочет автор, **не повторяя ошибок** старой. Старый код — источник знаний, а не основа.

Главный признак, что пора пересоздавать, а не чинить: каждая заплатка чинит один случай и ломает соседний; проверки спорят друг с другом; у одного и того же (например, положения руки) больше одного источника правды.

## Железные правила процесса

1. **Ни одной строки нового кода до шага 4.** Сначала знание, спецификация, полигон.
2. **Механику целиком не строить.** Один срез → автор проверяет на ощупь → следующий. Автор говорит «ок» — только тогда дальше.
3. **Одна правда.** У каждого состояния (поза, опора, хват) ровно один владелец. Остальные читают, не переписывают.
4. **Не накладывать слой проверки поверх системы, которой он не доверяет.** Если проверка и система расходятся — чинится система или проверка становится её частью (те же формы, те же данные).
5. **Старое не трогать,** кроме общих инструментов замера. Новое живёт рядом, с переключателем.
6. **Правило остановки:** правка ломает уже проверенное во второй раз → откат к последней точке «ок», пересмотр правила, а не третья заплатка.
7. **Коммит — только по просьбе автора.**

## Шаг 1. Раскопка старого (только чтение)

Прочитай документы проекта, шапки модулей, `git log` по модулю (сообщения коммитов — это история решений автора), откаты (`revert`) и их причины.

Собери три таблицы в один файл знаний (`design/<система>_knowledge.md`), если его ещё нет; если есть — дополни.

**Инвентарь поведения** — что работает и проверено автором (это нельзя потерять):

| Поведение | Где в старом коде | Как проверить | Источник (коммит / слова автора) |
|---|---|---|---|

**Журнал провалов** — что ломалось:

| Симптом (словами автора) | Корневая причина | Правило для новой системы |
|---|---|---|

**Скрытые правила** — разбросанные условия, пороги, исключения в старом коде (`if` с особыми случаями, магические числа). Для каждого: зачем оно было, нужно ли в новой системе, кто будет его владельцем.

Пороги и размеры (длины, высоты, скорости) выпиши отдельно с источником — новая система наследует их, если автор не сказал иначе.

## Шаг 2. Спецификация

- **Возможности** — список того, что система должна уметь, словами автора. У каждой — проверка «как понять, что работает» (сценарий + число).
- **Инварианты** — абсолютные правила (то, что не нарушается никогда), каждое с замером-сторожем.
- **Цель ощущения** — одна-две фразы на возможность: как это должно чувствоваться игроку.
- **Открытые вопросы** — всё, где желания автора противоречат друг другу или физике. Задай их автору **до** кода, коротко, с вариантами и своей рекомендацией.

## Шаг 3. Полигон и замер — до кода

- Сцена-полигон: по станции на каждый провал из журнала и на каждую возможность. Станции подписаны, между ними можно пройти.
- Автопрогон: бот проходит станции и печатает таблицу метрик (по инвариантам + успех + стоимость кадра).
- **Прогони полигон на старой системе** и сохрани отчёт — это нижняя планка. Новая система по каждой метрике должна быть не хуже, по инвариантам — ноль нарушений.

## Шаг 4. Архитектура (одна страница → одобрение автора)

- Блоки (компоненты с одной задачей) и общее состояние, которое они читают и пишут. Для каждого состояния — один владелец.
- Поток кадра: ввод → намерение → привод → физика → чтение результата → отрисовка. Где `Update`, где `FixedUpdate`.
- Для физических тел: **один способ привода на тело** (сустав с приводом ИЛИ кинематика ИЛИ сила), не смесь.
- Проверки достижимости и столкновений — теми же коллайдерами, что двигаются (sweep, penetration), не отдельной геометрией другой толщины.
- Бюджет: сколько запросов к физике и миллисекунд на кадр допустимо. Запросы — не на каждом подшаге физики.
- Как новая система включается рядом со старой (переключатель, отдельный префаб или сцена).

Покажи автору одну страницу. Без «ок» — не кодировать.

## Шаг 5. Срезы

Порядок срезов — по зависимостям (сначала то, без чего остальное не работает), каждый срез маленький. На каждый срез:

1. Правило в 1–2 предложениях + инварианты + цель ощущения.
2. **Матрица швов:** новый срез × каждый уже готовый блок × типовая геометрия (стена, угол, край, тонкая стена, щель чуть шире тела, верх и низ ступени, подвижная опора, ровно порог). По строке на ячейку, пустые пропусти.
3. Минимальная реализация отдельным блоком.
4. Прогон: полигон + сторожа на каждый кадр + регрессия уже готовых срезов. Сравни с прошлым отчётом — **каждое изменённое число**.
5. Отчёт автору: что прошло, что исправлено, что может проверить только он (ощущение). Числа — таблицей.
6. Автор играет. «Неудобно» — 2–3 варианта решения, выбирает автор.
7. «Ок» → строка в инвентарь поведения, точка отката (тег), коммит по просьбе.

## Шаг 6. Паритет и замена

- Новая система проходит весь полигон и регрессию не хуже старой, автор подтверждает на ощупь.
- Переключатель по умолчанию — на новую. Старая остаётся выключенной до явного «удаляем» от автора.

## Анти-паттерны (видел — остановись)

- Заплатка, которая «исправляет» результат другой системы задним числом (перезапись позы после физики, подтягивание цели к застрявшему объекту).
- Дискретный выбор вариантов, который может перескочить между кадрами (рывки). Нужна непрерывная величина с ограничением скорости.
- Сглаживание, которое тормозит то, что должно быть индикатором ввода.
- Проверка, которая отсекает почти все варианты рядом с собственным телом (застревание).
- Дорогой перебор на каждом подшаге физики (спираль падения ФПС).
- «Кисть / объект на длине руки в воздухе» — объект без опоры, когда опора обязана быть.
- Правило, разбросанное по пяти функциям с исключениями друг для друга.

## Что отдавать в конце сессии

- Обновлённый файл знаний (инвентарь, журнал провалов, открытые вопросы).
- Отчёт полигона: до (старая система) и после (новая) — таблицей.
- Что проверить автору на ощупь — коротким списком по станциям.
